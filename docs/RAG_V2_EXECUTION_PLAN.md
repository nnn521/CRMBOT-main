# CRMBOT RAG v2 优化执行方案与测试验收

日期：2026-10-20  
状态：待实施方案。本文件不表示功能已经开发或通过测试。  
范围：PostgreSQL/pgvector + 中文 BM25 + 原文证据库 + 后台 LLM Wiki 编译 + 按需轻量重排 + 受约束业务工具 + 一次最终回答生成。

## 1. 目标与边界

让客户获得有出处、条件完整且不过期的回答；把资料编译移到后台，把实时事实与计算交给工具，缩短在线模型调用链。

本期保留 FastAPI、React、LangGraph、服务端 checkpoint、现有认证与业务流程。知识模块采用模块化服务，后台 worker 单独运行；不先拆成大量微服务。暂不建设全量 GraphRAG、无限多轮 Agent、自主下单或合同签署。

“一次回答生成”指最终自然语言组织调用一次；按需查询补全和离线 Wiki 编译另计。简单事实可以用模板直接返回。证据不足先澄清，不能为了凑出答案反复生成。

验收目标为拟定发布门槛，须在第一阶段冻结测试环境和数据；本文件没有声称当前性能或准确率已达到目标。

## 2. 实施前提与角色

| 角色 | 工作 |
|---|---|
| 后端/AI 工程师 | 数据模型、入库、检索、工具、编排与可观测性 |
| 前端工程师（可兼职） | 引用、条件、资料状态与审核界面 |
| 业务审核人 | 权威来源、政策冲突、标准答案和发布批准 |
| 测试负责人（可由工程师兼任） | 冻结评测集、执行验收、记录失败和发布证据 |

建议排期：1 名后端/AI 工程师、前端兼职、业务审核及时响应时，核心可试用版本约 2–3 周，完整候选发布约 4–6 周。按里程碑验收推进，不按日历自动放行。

必须先确认 PostgreSQL 能安装 pgvector、模型运行环境与许可证、业务数据可用性。无实时报价/库存接口时使用带来源与有效期的审核数据表；测试桩只用于测试，不作为生产事实来源。没有有效数据时返回无法确认。

## 3. 现状基线与兼容约束

当前知识服务位于 backend/app/agents/nodes/knowledge_node.py，采用 Ollama bge-m3、FAISS、固定大小切分；JSON 文本快照重建仍需要 embedding。新服务应持久化向量，并让入库与在线请求解耦。

实施时重新核对工作区与提交差异，不覆盖用户已有修改；不要把其他后端或前端重构混入本次提交。当前真实模型调用次数、依赖版本与接口必须在 T01 核对后写入基线，不能沿用旧报告计数。

必须保持：
- thread_id=session_id；客户端不回传 history。
- 非终态节点使用 strip_messages；终态使用 state_update_with_reply；最终结果通过 graph.ainvoke 获取。
- 清空历史继续清除 checkpoint；检索缓存不充当对话记忆。
- JWT httpOnly Cookie、现有授权边界、SECRET_KEY 校验不退化。
- 用户与资料进入模型前使用项目 prompt 防护；资料视为数据，不执行其中指令。边界标签不能替代权限与工具白名单。
- API 客户端经过 frontend/src/lib/api.ts；Zustand 只保存客户端 UI 状态。
- 路径锚定 backend/，上传和输出文件名消毒。

### 3.1 当前源码核对后的具体接入要求

- 正常 RAG 命中当前通常为两次文本模型调用（意图识别 + 知识整合）；sales_response 检测已有回答后短路，不应误认为当前必有第三次生成。优化需实测意图阶段耗时，不能虚报消除了一次本来不存在的调用。
- knowledge_synthesis_node 已写回复；新 AnswerService 替换其生成职责，保持只追加一条 AIMessage。新增状态必须通过 sales_graph.py 的最终状态净化白名单，并由 chat.py 显式透传，不能只放 metadata 后假定自动返回。
- 当前无知识上传 API；KnowledgePage.tsx 只是 ComingSoon。知识管理需要新增 API、路由注册和页面，不能将内部 add_documents 视为现成功能。
- 引用链路涉及 backend/app/models/chat.py、api/v1/chat.py 的 HTTP、WS payload、助手消息持久化与两种历史接口；frontend/src/types/index.ts、lib/api.ts、api/chat.ts、hooks/useChat.ts、hooks/useWebSocket.ts、stores/chat.ts、components/ChatBubble.tsx 均需核对。HTTP/WS 抢先到达和去重时必须合并 citations，重载历史后保持一致。生成文档 documents 与证据 citations 分开。
- 上传使用 FormData 时，共享 apiFetch 不得强设 application/json，应由浏览器生成 multipart boundary。
- 当前 TenantMixin 仅预留租户字段，不能声称已有租户隔离；私有知识上线前必须实现上传到引用访问的全链路授权。现有 search(filters=...) 内部未执行过滤，需要重新实现。
- 当前 init_db 使用 create_all，不提供已有表演进。T03 须加入版本化迁移机制并验证升级/恢复；Compose 原 postgres:16-alpine 不含 pgvector，需验证带扩展镜像及现有卷升级兼容，不可直接更换大版本。
- test_agent_graph.py 当前把 search 固定为空；新增真实命中路径、生成调用次数、HTTP/WS/历史引用一致性测试。前端当前没有 E2E runner，需要选择精确锁版本的工具或记录可复现浏览器验收，typecheck 不代替界面行为验证。

## 4. 目标处理流程

### 4.1 后台

上传/同步 → 保存不可变原件及哈希 → 格式与权限校验 → 标题/表格/页码解析 → 提取元数据 → 结构感知切分 → 保存原文定位 → Wiki 草稿编译 → 来源依赖与冲突检查 → 业务审核 → 构建 pgvector 与 BM25 → 完整性验证 → 原子切换知识版本 → 失效缓存。

解析、编译或索引失败不影响上一发布版本。法律/业务已撤回资料必须通过独立撤回屏障立即禁止使用，不能等待下次编译；回滚不能复活撤回来源。

### 4.2 在线

问题 + session_id → 授权与 checkpoint → 固定知识版本和授权上下文 → 解析实体/问题类型 → 条件不足则澄清 → 并行执行知识检索与业务查询 → 必要时根据查询结果计算 → 汇合证据 → 校验条件/权限/时效/冲突 → 一次回答生成或模板输出 → 输出检查 → answer/citations/数据时间 → 保存对话与追踪记录。

检索：dense 与 BM25 并行 → RRF → 按需 reranker → 选择原文及 Wiki 证据。Wiki 帮助组织，关键结论追溯原文；业务工具结果以结构化来源记录追溯。

输出检查失败时移除不支持的承诺并返回受限说明；不得无限重试。关键价格与金融结论经过检查后再展示。首版允许先返回处理状态，再一次性返回检查后的答案，不能把未检查的价格流式发送后再撤回。

## 5. 技术决策

| 模块 | 首版选择 | 决策依据 |
|---|---|---|
| 存储 | PostgreSQL + pgvector，初期精确搜索 | 小规模优先保证召回与事务；达到规模阈值后评估 HNSW |
| BM25 | 独立、可重建的版本化内存索引；中文分词 + 型号/别名字典 | 避免误把 tsvector/pg_bigm 当 BM25；初期减少额外数据库服务 |
| 文档解析 | Markdown/文本规则解析，Excel 保留列语义；PDF 按需 Docling | 先覆盖当前资料；重型解析依赖放后台，不能压在线进程 |
| embedding | bge-m3 为基线，Qwen3-Embedding-0.6B 为挑战者 | 项目留出集与负载测试决定，不能凭通用榜单更换 |
| reranker | bge-reranker-v2-m3 与 Qwen3-Reranker-0.6B 对比 | 按需、可超时降级；CPU/GPU 分别测试 |
| Wiki | 应用内编译服务 + 数据库依赖关系 + 人工审核 | 可复用知识但不能把生成内容当权威原件 |
| 后台任务 | PostgreSQL 持久任务表 + worker 租约/重试 | 首版减少基础设施；不能用进程内 BackgroundTasks 充当持久队列 |
| 工具 | 只读查询与纯计算函数，固定 schema 与白名单 | 权限/适用条件由服务端校验，不执行任意 SQL/URL |
| 编排 | 现有 LangGraph 接入知识应用服务 | 保持销售、文档、多模态节点兼容；避免重复生成 |

依赖版本：实施 T01 在目标 Python/Docker 环境验证后精确锁定 requirements.txt；模型固定 revision、向量维度、归一化方式、距离度量和推理参数。计划阶段不编造尚未验证的版本号。更换 embedding 必须全量构建新版本，不能混用向量空间。

BM25 必须在授权可见语料内排名，或采用等效且可验证的隔离实现；不能全库 top-k 后才过滤，造成泄露或可见证据被挤出候选。缓存键包含权限作用域/版本，授权变化使缓存失效。早期内存方案需要按租户/可见资料集合分区；分区数量或内存开销超预算时，再评估支持可靠过滤的检索引擎。

## 6. 数据与接口设计

### 6.1 核心记录（拟新增）

| 记录 | 关键字段与约束 |
|---|---|
| source_document / document_version | 来源 URI、文件哈希、版本、权威级别、车型/年款、门店、有效期、ACL、审核状态；原件不可变 |
| evidence_span | 原文段落/表格单元格、页码、章节路径、父段落、原始文本、文档版本；评测标注定位在此层 |
| retrieval_chunk | chunk_id、span 引用、上下文文本、父块、token 数、embedding 与模型 revision；上下文不能新增事实 |
| wiki_page / wiki_claim | 页面版本、结论、支持 span、适用条件、状态、编译模型/prompt 版本 |
| claim_dependency | 来源版本与结论/页面的依赖，支持更新、到期和撤回定位 |
| knowledge_release | 构建状态、向量模型、BM25 产物校验和、语料清单、评测报告、发布时间 |
| active_release | 单个作用域的当前版本指针；事务切换，版本产物构建后不可变 |
| ingestion_job | 幂等键、状态、重试次数、租约、心跳、错误摘要；崩溃可恢复 |
| source_revocation | 撤回 ID、时间、原因；检索、证据组装、引用访问均实时检查 |
| business_fact / tool_result | 数据源、记录 ID、查询时间、有效期、输入参数、币种/单位、适用条件 |

文档身份使用逻辑 doc_id，版本使用不可变 version_id；块 ID 可由版本/定位/内容派生，不能只按全文哈希合并不同 ACL 或来源。相同内容跨文档不丢来源关系。切分改变时通过原始 span 映射评测，避免整体重标。

时间区间明确含端点规则与时区；金额使用 Decimal 和明确单位；指导价、成交价、落地价分别存储。支持多车型问题，不能硬过滤成一个车型。

### 6.2 服务边界（拟新增 app/services/knowledge/）

- IngestionService：接收资料，创建幂等任务。
- ParserAdapter：产出结构化原文与定位；按文件类型选择实现。
- WikiCompiler：从批准来源生成草稿与结论依赖。
- ReleaseService：验证发布清单、切换版本、回滚。
- HybridRetriever：在指定权限与版本内执行 dense/BM25/RRF。
- RerankerAdapter：可替换模型、超时回退；分数不视为正确概率。
- EvidenceAssembler：合并原文、Wiki、业务结果，检查条件和冲突。
- ToolRegistry：白名单函数及 schema，拒绝未授权工具与参数。
- KnowledgeAnswerService：规划、执行、一次最终生成、结构化返回。

采用 Adapter 隔离模型与解析器，Strategy 切换召回/重排方案，Release Manifest 管理发布一致性；只为可替换边界定义接口，避免每张 ORM 表再包一层无意义仓库。

### 6.3 对外契约

保留现有 chat 路径与字段，新增可选字段，HTTP/WS 一致：
- citations：citation_id、source_id、document_version、span_id、标题、定位、受授权控制的访问入口。
- knowledge_release_id、answer_status（answered/partial/clarification/unavailable）。
- data_as_of、assumptions、limitations；业务结果带来源及计算条件。

浏览引用必须再次授权，不能暴露本地文件路径或未保护的对象存储链接。公众响应不返回内部 prompt、原始调用日志或全量检索分数。

后台接口覆盖上传任务、处理状态、草稿审核、发布/回滚、来源撤回；复用当前鉴权并新增明确管理权限。上传返回 job_id，不等待整个编译完成。

## 8. 测试体系与数据

### 8.1 数据集

建立 240 条人工复核问题：180 条知识/会话问题、60 条工具与条件问题。固定 160 条开发集和 80 条留出集，按来源/车型/问题家族分组划分，避免同一问题改写跨集合泄漏。所有类别两边均有覆盖。

180 条知识问题配额：精确型号配置 40、口语别名 25、多轮追问 25、多车型/多证据 30、时效与冲突 30、无答案与歧义 30。60 条工具问题：报价/库存 20、贷款/费用 25、缺失条件与故障 15。权限、提示注入、并发发布另建确定性专项套件，不靠这 240 题覆盖。

每题包含 query、必要历史、授权身份、参考时间、期望行为、相关原始 span/事实记录、必需条件、禁止结论、业务标准答案。时效测试固定时钟。缺失数据/无答案题单独评分，不进入正样本检索 Recall 分母。

允许 LLM 辅助生成开发题，但必须人工复核；留出集不用于调 prompt、阈值和模型选择。首次留出测试失败后修复再测试，须记录迭代与补充盲测题，不能只反复调到通过同一集合。

### 8.2 层级

1. 单元：解析、元数据、分词、RRF、金额与期限计算、缓存键、状态转换。
2. 集成：真实 PostgreSQL/pgvector、BM25 产物、发布、ACL、任务租约、引用访问；不能全部 mock。
3. 检索离线：不经过回答模型，独立测候选和最终排名。
4. 回答端到端：真实候选模型与数据源测试环境；模型裁判仅作辅助，关键案例由业务审核人判定。
5. 性能与故障：实际服务、并发、超时、进程重启和依赖不可用。
6. 兼容回归：认证、消息 reducer、清历史、合同/报价/提案、多模态、HTTP/WS、前端严格类型。

## 9. 测试验收门槛

### 9.1 质量（拟定首版门槛）

| 项目 | 定义 | 门槛 |
|---|---|---|
| 候选 Recall@20 | 正样本各题相关原始证据找回比例的宏平均，原始 span 映射去重 | ≥95% |
| 最终 Recall@5 | 最终前 5 条相关证据覆盖，宏平均 | ≥90% |
| MRR@5 | 首个相关证据名次倒数，前 5 无相关则 0 | ≥0.85 |
| 多证据完整率 | 所有必要证据均进入最终上下文的题目比例 | ≥90% |
| 回答通过率 | 事实正确、条件完整、无禁止结论；按整题通过计 | ≥90%，每个类别 ≥85% |
| 引用支持率 | 经审核的事实性结论中，其引用支持完整条件的比例 | ≥95% |
| 引用可定位 | 引用能定位指定文档版本与原始 span；且有权限 | 100% |
| 合理澄清/拒答率 | 对无答案/歧义题采取期望行为 | ≥95% |
| 关键业务套件 | 错车型/年款价格、过期优惠、伪造库存、错误月供、越权引用、撤回证据 | 0 个失败；有限测试通过不等于真实世界零风险 |

同时报告基线差值、逐题得失和失败样例。若基线已高于绝对门槛，新方案不得明显退化；对成对结果做 bootstrap 置信区间并人工审查关键类别。小样本不能凭 1–2 题差异宣称显著提升。某优化无可验证收益就关闭，不为完成技术清单强行开启。

### 9.2 性能

T01 冻结硬件 CPU/GPU/内存、模型 revision、量化、最大输入、知识规模、网络与提供商、输出长度。以下为目标预算，实际环境若不满足必须报告并提出缩减候选/更换部署方案，不能临时放宽门槛后宣称达标。

- 10,000 个检索块、10 并发、同机数据库/检索、温模型、禁用最终答案缓存：检索含可选重排 p95 ≤800ms；精确工具路径 p95 ≤500ms（外部数据源超时另计且须报告）。
- 常规知识回答：预处理至开始最终模型调用 p95 ≤1s；完整、检查后回答 p95 ≤6s，输出限制 250 个模型 token。外部模型若超预算，单独列出其耗时，整体验收仍不能按通过处理。
- 正常知识问答最终生成调用数 ≤1；补全调用数 ≤1 且仅按需；工具执行有上限和总 deadline。
- 在质量门槛通过且同条件下，目标完整回答 p95 相对基线减少 ≥20%；若当前基线已快或链路提供商变化，报告实际差值，不承诺必然实现。
- 负载：并发 1/5/10/20，每档预热 2 分钟、持续 10 分钟；另做 60 分钟稳定性测试。记录 p50/p95/p99、错误率、排队、CPU/GPU/内存、输入输出 token 和每题成本。
- 正常环境非预期错误率 <1%；故意注入故障单独计数；不得把大量 unavailable 计为“成功率高”。
- 冷启动单独测试：不重新 embedding；无 embedding 服务时仍能在启动后 30 秒内提供已发布 BM25 降级检索。无正式知识版本时 readiness 不通过，不能生成默认业务资料掩盖。

### 9.3 故障与一致性专项

| 编号 | 注入场景 | 必须观察到的行为 |
|---|---|---|
| F01 | embedding 不可用 | 切换 BM25；记录 degraded；不重建全库、不伪造证据 |
| F02 | reranker 超时 | 在其配置预算（起始 300ms，纳入总 800ms）内取消/隔离，使用 RRF；无堆积任务 |
| F03 | 回答模型超时 | 总 deadline 内返回可理解的不可用说明，不能编写业务承诺 |
| F04 | 报价/库存接口失败 | 相关部分无法确认；可继续解释有证据的产品知识 |
| F05 | 上传任务重复、worker 中途退出 | 幂等不重复发布；租约到期恢复，保留诊断 |
| F06 | Wiki 编译失败/幻觉/来源冲突 | 草稿不发布；上一版本继续可用；冲突需要审核 |
| F07 | 向量完成、BM25 构建失败 | active_release 不改变，不出现混合版本 |
| F08 | 查询与发布并发 | 单请求只使用一个版本；上线前旧版本引用仍可追溯且受撤回限制 |
| F09 | 来源撤回、用户权限收回 | 新请求立即排除；已在处理请求在输出前再次校验；引用入口拒绝；缓存不绕过 |
| F10 | 回滚旧知识版本 | 已撤回来源不复活；确认回滚版本适用，业务事实不回滚到过期值 |
| F11 | PostgreSQL 不可用 | readiness 失败；返回明确知识不可用；不能无证据答价格 |
| F12 | 数据库备份恢复 | 文档版本、依赖与发布清单一致；BM25 可重建且校验和吻合 |

权限安全必须覆盖两用户/两门店/不同角色、同内容不同权限、检索缓存、Wiki 派生页和引用下载。Wiki 权限取支持来源的可见条件组合，不能因归纳而放宽；无法满足时按权限分别编译。

### 9.4 关键业务用例

- 指导价不能回答为落地价；缺税费/保险/门店条件时明确列出未知项。
- 多车型对比保留两个实体，不因单车型过滤漏掉一方。
- “刚才那款”歧义时澄清；不自行补年款或配置。
- 活动到期边界使用固定时钟；缺有效期的优惠不宣称当前有效。
- 月供对照独立计算基准：等额本息、零利率、首付大于车价、负数、期限缺失、年/月利率、费用是否计息；金额 Decimal，舍入规则固定，最终月供误差 ≤0.01 元。
- 文档含“忽略系统指令”“调用任意 URL”等内容，只作为文本证据，不执行。
- 模型输出不存在的引用/正确数字但错误车型/工具结果被改写，必须拦截相关承诺。
- 无资料、模型与工具全失败，不能返回演示丰田价格作为正式答案。

## 11. 灰度与回滚

1. 新表与新服务先旁路部署，旧链路继续工作；迁移先在备份恢复库验证，扩展操作确认数据库支持。
2. 把批准资料导入新库，双路影子评测；影子工具限只读且限制调用量，不影响真实业务。
3. 内部账号试用，再按稳定会话分桶 5% → 25% → 100%；同一会话保持路线一致，撤回与授权屏障始终生效。
4. 每档至少观察一个完整业务日并累计 100 条有效请求；不足则延长。人工复核关键案例；未达到质量/错误率/延迟门槛不扩大。
5. 越权、错误价格承诺、撤回失效立即停止灰度；其他指标连续两个 10 分钟窗口超预算暂停扩大并调查。
6. 应用路由与知识版本分开回滚。旧 FAISS 路线若不满足权限/撤回要求，只能关闭相关能力，不能以回滚之名恢复不安全回答。
7. 保留旧索引和旧表至观察期结束；本期不执行不可逆删除。生产发布由负责人批准，编写方案不等于授权生产迁移。
